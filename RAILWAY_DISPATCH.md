# The dispatch cron services

Two Railway cron services, in the same project as the web app, run
`scripts/dispatch_workflows.py` on a schedule. Each run POSTs a
`workflow_dispatch` to every hazard workflow listed in
`pipeline.publish_schedule.HAZARD_WORKFLOWS` (IFR, MTN OBSC, TANGO).

| Service | When | `trigger` it sends | Covers |
|---|---|---|---|
| **Primary** | +1:20 after 03/09/15/21Z | `railway-cron` | the normal path, timed to NBM's arrival |
| **Backstop** | +2:30 | `railway-backstop` | a primary dispatch that didn't happen (missed or crashed run, expired token) |

Behind both, each workflow keeps one GitHub `schedule:` entry at +3:37 as
the last resort, for a Railway outage. The trigger lives on Railway because
GitHub delays `schedule:` runs: ~95 minutes on 2026-09-07, up to 4.5 hours
by 2026-09-10, and over 2026-10-28 to 11-11 it fired 2–356 minutes late
and skipped about two slots in five. See [METHODS §8.9](docs/METHODS.md).

## Both services are configured by their service settings

Railway has deprecated **Config as Code** (`railway.json` / `railway.toml`,
including a custom path like `railway.dispatch.json`): Railway stops reading
existing files on **2026-12-01**, and new services cannot opt in. It has
also deprecated the **Nixpacks** builder; **Railpack** is the default.
So both services are described here by the settings you enter in the
Railway UI, and nothing in this repo is read by Railway to configure them.

| Setting (Railway UI) | Primary (+1:20) | Backstop (+2:30) |
|---|---|---|
| Source → GitHub repo / branch | this repository / `main` | this repository / `main` |
| Build → **Builder** | `Railpack` | `Railpack` |
| Deploy → **Custom Start Command** | `python3 scripts/dispatch_workflows.py` | `python3 scripts/dispatch_workflows.py --trigger railway-backstop` |
| Deploy → **Cron Schedule** | `20 4,10,16,22 * * *` | `30 5,11,17,23 * * *` |
| Deploy → **Restart Policy** | `Never` | `Never` |
| Config-as-code → Railway Config File | *(empty)* | *(empty)* |
| Variables → `GITHUB_TOKEN` | the primary's fine-grained PAT | the backstop's **own** fine-grained PAT |
| Variables → `GITHUB_REPOSITORY`, `DISPATCH_REF` | not set (defaults are correct) | not set (defaults are correct) |
| Networking → public domain, healthcheck | none | none |

Why each one matters:

- **Custom Start Command must be set explicitly.** Without one, Railpack
  falls back to the repo's `Procfile`, whose `web` entry is the *web app*
  (`uvicorn webapp.main:app …`). A dispatcher started that way would serve
  HTTP instead of dispatching, and never exit.
- **Restart Policy: Never.** A cron job that restarted on exit would POST
  the dispatches again in a loop. Railway's default is On Failure.
- **Cron Schedule** is UTC. Both lines are generated by
  `pipeline.publish_schedule.dispatch_cron_entry()`; print them with
  `python3 scripts/dispatch_workflows.py --print-schedule` (add
  `--trigger railway-backstop` for the backstop's).
  `tests/test_railway_settings_doc.py` fails if this table drifts from the
  schedule module or from the dispatcher's own flags.
- **Railpack** detects Python from `requirements.txt` and installs it. That
  is the web app's dependency list, which the dispatcher (stdlib only) does
  not need; it makes the build slower, not the run, and is harmless.
- **Railway Config File stays empty.** Railway's migration guidance is to
  clear that field; a service still pointed at a config file is "managed by"
  it until 2026-12-01.
- **Tokens:** fine-grained PATs, **Only select repositories** → this
  repository, **Actions: Read and write** and nothing else. Give the two
  tokens different expiry dates so they never lapse on the same day.
  `GITHUB_TOKEN` is the variable the script reads on both services;
  Railway variables are per service, so each holds its own token.

## Moving the primary off `railway.dispatch.json` (before 2026-12-01)

The primary was set up pointing at `railway.dispatch.json`, which supplies
its start command, restart policy and Nixpacks builder. Do these **in this
order**, because clearing the file before the start command is set would
leave the `Procfile` fallback above in charge:

1. Settings → Deploy → **Custom Start Command**:
   `python3 scripts/dispatch_workflows.py`
2. Settings → Deploy → **Restart Policy**: `Never`.
3. Settings → Deploy → **Cron Schedule**: confirm `20 4,10,16,22 * * *`.
4. Settings → Build → **Builder**: `Railpack`.
5. Settings → Config-as-code → **Railway Config File**: clear the field.
6. Redeploy, then check the next run (04:20, 10:20, 16:20 or 22:20Z): the
   Railway log should show one `DISPATCH … status=204` line per hazard, and
   each hazard's GitHub run an `NBM-ARRIVAL … trigger=railway-cron` line
   with `start_delay_min` near 0.

## Setting up the backstop from scratch

1. **Create the token** (GitHub → Settings → Developer settings →
   Fine-grained personal access tokens): this repository only, **Actions:
   Read and write**, an expiry different from the primary's, named e.g.
   `gairmet-dispatch-backstop`.
2. **New Service → GitHub Repo → this repository**, then enter the
   Backstop column of the table above.
3. **Check it** after the first run (05:30, 11:30, 17:30 or 23:30Z): one
   `DISPATCH … status=204` line per hazard in Railway, and each hazard's
   GitHub run ending with `SKIPPING PUBLISH [already-published]` (the
   normal case) or an `NBM-ARRIVAL … trigger=railway-backstop` line (it had
   work to do).

## Checking without deploying

```
python3 scripts/dispatch_workflows.py --dry-run                               # primary: URLs + payload, sends nothing
python3 scripts/dispatch_workflows.py --trigger railway-backstop --dry-run    # backstop
python3 scripts/dispatch_workflows.py --print-schedule                        # 20 4,10,16,22 * * *
python3 scripts/dispatch_workflows.py --print-schedule --trigger railway-backstop   # 30 5,11,17,23 * * *
```

## If a run fails

The job exits non-zero, so Railway marks the run failed and the status
line says why: `status=401` is an expired or wrongly scoped token,
`status=422` a bad ref or a workflow without a `workflow_dispatch` trigger,
`status=no-response` a network failure. The cycle is still covered by the
other service and then the +3:37 GitHub `schedule:`; the non-zero exit is
what tells somebody to fix this one.

## The old config files

`railway.dispatch.json` and `railway.backstop.json` are still in the repo,
for now, as a record of what the services ran before. Railway stops reading
Config as Code on 2026-12-01, and the backstop (created on Railpack with UI
settings) never read its file. Remove both once the primary has been moved
off its file and has dispatched on the new settings.
